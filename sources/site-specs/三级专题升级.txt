# 第四章：三级长尾关键词发现系统

## 4.1 建立持续运行的三级关键词工作流

三级文章应形成以下流程：

**二级专题 → 搜索意图 → 用户具体问题 → 长尾关键词 → 文章标题 → 完整正文 → 内链 → 搜索流量 → 下一步用户需求。**

为每个二级专题自动识别相关的：

- 问题型关键词。
- 教程型关键词。
- 比较型关键词。
- 故障型关键词。
- 价格型关键词。
- 使用场景关键词。
- 设备型号和操作系统关键词。
- 品牌相关关键词。
- 替代方案关键词。
- 年份、版本及更新关键词。

长期维护，而不是只生成一次关键词列表。

## 4.2 关键词来源

整合：

1. 现有关键词文件。
2. 一级、二级专题的关键词映射。
3. 已发布文章标题和正文。
4. 项目里的长尾问题库。
5. 品牌资料中的真实产品信息。
6. 已收录的用户常见问题。
7. 可合法访问的公开搜索建议。
8. Google Search Console 导出数据。
9. Bing Webmaster Tools 导出数据。
10. 真实的站内搜索词。

如果无法获取真实搜索量、搜索展示量或关键词难度，不允许编造。

可将尚未验证的候选关键词标记为 `discovered` 或 `unverified`。

## 4.3 搜索意图分类

至少识别：

- Informational：知识解释。
- How-to：操作教程。
- Troubleshooting：故障排查。
- Comparison：方案比较。
- Commercial Investigation：购买前研究。
- Navigational：寻找特定软件或品牌。
- Transactional：购买、注册或领取。

一个页面应以一个明确的主要搜索任务为中心。

同一搜索意图可以覆盖多个自然相关长尾词，不需要每个关键词建立一个新 URL。

## 4.4 建立关键词映射数据结构

每条文章任务至少包含：

- keyword
- primaryKeyword
- secondaryKeywords
- longTailQuestions
- searchIntent
- audience
- contentType
- parentTopic
- parentCluster
- targetUrl
- articleTitle
- contentOutline
- existingUrl
- relatedArticles
- relatedBrands
- conversionIntent
- contentPriority
- contentStatus
- sourceRequirements
- lastReviewedAt

建立统一的文章待办系统。

# 第六章：三级文章生产标准

## 6.1 内容长度

普通长尾文章：

**2,500—5,000 个有效中文汉字。**

核心技术教程、综合故障指南及比较文章：

**4,000—8,000 个有效中文汉字。**

特殊复杂问题根据实际信息需要扩展。

不使用固定字数代替内容质量。

不把导航、代码、重复表格、FAQ 标签和页脚计入有效正文。

## 6.2 文章结构

每篇三级文章应结合搜索意图设置：

1. 独立 Title。
2. 独立 Meta Description。
3. 与任务一致的 H1。
4. 开头直接回答问题。
5. 适用范围和前提条件。
6. 核心步骤、比较或解释。
7. 实例、截图或验证方法。
8. 容易出现的错误。
9. 结果判断。
10. FAQ。
11. 所属二级专题入口。
12. 相关三级文章。
13. 相关评测或其他下一步内容。
14. 来源与更新时间。

这不是所有文章必须统一使用的章节顺序。

文章结构必须由具体问题决定。

## 6.3 不同类型文章采用不同正文模式

### 教程文章

使用：

适用系统 → 准备事项 → 实际操作 → 成功验证 → 常见错误。

### 排障文章

使用：

症状判断 → 原因分类 → 逐项检查 → 修复操作 → 验证结果。

### 比较文章

使用：

比较结论 → 比较表 → 关键区别 → 适用人群 → 条件与限制。

### 知识文章

使用：

概念定义 → 技术原理 → 实际影响 → 使用场景 → 常见误区。

### 价格文章

使用：

费用结论 → 真实套餐 → 价格计算 → 使用成本 → 适合人群 → 风险。

### 风险文章

使用：

问题概况 → 证据来源 → 确认事实 → 未确认事项 → 应对建议 → 后续选择。

## 6.4 每篇文章都必须有信息增量

新增内容至少解决：

- 用户不知道怎么操作。
- 用户不知道如何选择。
- 用户不理解技术术语。
- 用户无法判断错误原因。
- 用户不知道不同方案的限制。
- 用户缺少真实比较依据。

避免大量类似：

“随着互联网的发展……”

“在数字化时代……”

“选择合适的服务十分重要……”

等缺乏实际信息的开场白。

# 第七章：品牌深度评测矩阵

## 7.1 品牌评测定位

品牌评测是三级文章流量进入商业决策阶段的重要承接页面。

**评测页负责帮助用户判断品牌，而不是简单复述品牌的广告介绍。**

重点回答：

- 这家机场怎么样？
- 真实套餐如何？
- 有什么优势和限制？
- 线路与客户端有什么特点？
- 是否适合当前用户？
- 和同价位品牌相比如何？
- 是否值得进一步了解和购买？

每家品牌建立独立评测 URL。

建议：

`/reviews/{brand-slug}/`

正式 URL 以现有项目为准。

不得出现同一品牌多个内容高度重复的评测入口。

## 7.2 读取全部品牌资料

从项目现有品牌库读取全部品牌，不以固定数字硬编码。

重点包括：

光速云、暮光加速、飞猫云、微风网络、大佬云、星岛梦、二猫云、无忧链接、唯兔云、Firefly、宇宙云、U1S1、灵猫网络、极连云、光年梯、一翻云、SOGO 云、可信云、速界、闪跃、全球云、闪电鼠、云界线、榴莲云、神行加速、环球梯、隐形人、梯子云、灵动云、浪网、边缘节点 EdgeNova。

文件名虽然标注 32 家，但必须按真实品牌身份去重，不得为了凑数虚构品牌。

Firefly 的重复记录、历史入口和不同链接需要特别核对。

主推品牌为光速云，编辑展示优先级从项目配置读取。

商业展示顺序与客观评测排序必须分开管理。

## 7.3 每家品牌独立万字级评测

当真实资料充足时，以 **9,000—12,000 个有效中文汉字** 为深度编辑目标。

对于资料丰富的重点品牌，可以扩展至 12,000—15,000 字。

如果资料不能支撑目标篇幅，优先完成准确内容，列明具体资料缺口，不能用无依据的测试或重复宣传凑字数。

每家品牌评测应覆盖：

### A. 直接评测结论

开头回答：

品牌整体定位、主要优势、核心限制、适用人群及目前资料可信度。

### B. 品牌背景

包括：

- 品牌名称。
- 历史与运营情况。
- 服务定位。
- 官方资料。
- 资料来源。
- 数据核实日期。

### C. 套餐完整分析

覆盖有资料支持的真实套餐：

- 套餐名称。
- 价格。
- 付款周期。
- 流量额度。
- 流量重置周期。
- 设备数量限制。
- 线路权益。
- 优惠码。
- 适用条件。

如果存在 4—5 档或更多套餐，应展示有代表性的不同价格和流量层级。

不足 4 档时不得虚构。

### D. 线路与节点

分析：

- 线路类型。
- 协议。
- 节点覆盖。
- 地区分布。
- IP 特点。
- 线路倍率。
- 适合的应用需求。

区分品牌方声明与独立验证信息。

### E. 测速分析

使用现有可核实的测速图片和数据。

说明：

- 测试日期。
- 测试环境。
- 测试节点。
- 延迟。
- 下载速度。
- 上传速度（如有）。
- 丢包率（如有）。
- 测试限制。

不能把一般时间段的测速自动标记为晚高峰测试。

### F. AI 与流媒体

分析：

- ChatGPT。
- Claude。
- Gemini。
- Netflix。
- Disney+。
- YouTube。
- 其他资料中实际覆盖的服务。

每个项目区分：

已实测、品牌声明、部分可用、未测试。

### G. 客户端兼容

分析：

- 自研客户端。
- 第三方客户端。
- Windows。
- macOS。
- Android。
- iOS。
- Linux。
- 订阅格式。
- 使用难度。

不能把只支持官方账号登录的品牌写成支持任意第三方订阅。

### H. 优势与限制

分别说明：

- 适合什么人。
- 不适合什么人。
- 核心竞争力。
- 真实使用限制。
- 价格优势或劣势。
- 测试资料中的不足。
- 运营与售后注意事项。

### I. 同价位品牌比较

选择真实相关的 2—4 家品牌比较。

根据主题选取：

- 套餐价格。
- 流量额度。
- 倍率。
- 客户端兼容。
- 线路信息。
- AI/流媒体支持。
- 风险和售后条件。

只有同等口径的数据才进行直接数值排名。

### J. 用户选择建议

针对不同使用情况给出建议：

- 轻度用户。
- 新手。
- 多设备用户。
- AI 工具用户。
- 流媒体用户。
- 重度流量用户。
- 预算有限用户。

结论必须有条件，不使用绝对化营销表达。

### K. FAQ

整理约 8—15 个与该品牌相关的实际问题。

### L. 最终评价

总结：

品牌定位、主要优势、核心局限、适合人群和选择前注意事项。

随后提供自然且透明的品牌详情或注册入口。

## 7.4 每家品牌必须拥有不同的内容结构

不同品牌不能使用完全相同的 20 个章节顺序。

例如：

**光速云**

优先分析套餐层级、线路资料、客户端兼容及综合使用场景。

**飞猫云**

优先分析专属客户端模式、新手操作体验和不同设备使用限制。

**二猫云**

优先分析套餐层级、多设备支持及不同流量用户的选择。

**星岛梦**

优先分析节点地区、套餐类型与多场景适用条件。

**隐形人**

优先分析独立客户端、第三方订阅限制和售后服务声明。

**灵动云**

优先分析历史测试资料、线路信息和真实测试条件。

**边缘节点 EdgeNova**

优先分析多线路分配定位、套餐结构及仍需核实的性能数据。

每家品牌根据真实资料形成独有章节，不能只改变颜色、品牌名称和数字。

# 第八章：品牌资料可信度与冲突检查

## 8.1 建立统一数据状态

必须区分：

- verified：有依据且经过核实。
- measured：明确条件下的实测。
- vendor：品牌方声明。
- historical：历史资料。
- unverified：尚未核实。
- conflicted：存在资料冲突。

在品牌评测中明确说明数据状态。

## 8.2 特别检查已有冲突

例如：

- 光速云轻量版曾出现不同月流量记录。
- Firefly 存在重复品牌资料和不同推广链接。
- 部分品牌的最低月价实际上属于年付折算。
- 部分套餐属于历史价格。
- 某些品牌只提供部分测速数据。
- 一些品牌的 IEPL/IPLC 信息属于品牌自述。
- 部分品牌的 AI 解锁能力需要具体节点测试。
- 某些品牌只有专属客户端。

冲突没有解决时，不能单方面把一个版本标为已经验证的当前数据。

建立数据冲突报告。

## 8.3 测试图表

读取品牌图表样式文件，复用现有专业监控面板设计。

至少支持：

- Performance Monitoring Report。
- Service Availability Matrix。
- Network Path Observatory。
- Infrastructure Service Snapshot。

保留深色技术监测图表与简白正文网站的视觉区分。

有真实测试数据时生成对应数据图表。

没有实测数据时，可生成品牌规格信息图、套餐图或注明为概念示意的技术图，但不得把示意数据标成真实测试。

# 第九章：品牌评测与商业页面分离

## 9.1 品牌评测页面

建议：

`/reviews/{brand-slug}/`

主要关键词：

品牌名 + 评测、怎么样、靠谱吗、稳定吗、适合谁。

核心任务：

帮助用户做选择。

内容重点：

真实资料、独立分析、优缺点、比较、适用场景、风险和选择建议。

## 9.2 品牌商业详情页面

建议：

`/brands/{brand-slug}/`

主要关键词：

品牌名 + 套餐、价格、优惠码、注册、官方入口。

核心任务：

帮助用户了解套餐和进入正确的注册入口。

页面至少包含：

- 品牌核心介绍。
- 当前可核实套餐。
- 4—5 个代表性套餐卡片（资料足够时）。
- 套餐比较表。
- 优惠码及条件。
- 客户端兼容。
- 购买前注意事项。
- 常见问题。
- 深度评测入口。
- 注册 CTA。

品牌商业页不能直接复制万字评测正文。

品牌评测和品牌商业详情要具有不同搜索意图。

## 9.3 品牌对比文章

针对确实具有比较价值的品牌，建立独立对比文章。

例如：

- 光速云与飞猫云的差异。
- 光速云与二猫云的套餐比较。
- 飞猫云与星岛梦的新手使用比较。
- 同价位机场套餐对比。
- 专属客户端品牌与第三方订阅品牌比较。

对比页面的 URL 可采用：

`/compare/{brand-a}-vs-{brand-b}/`

每篇比较文章必须包含：

1. 简明比较结论。
2. 同口径核心参数表。
3. 价格和流量比较。
4. 线路及客户端差异。
5. 使用场景差异。
6. 各自适合人群。
7. 资料和测试限制。
8. 两个品牌各自的详细评测入口。
9. 两个品牌各自的套餐详情入口。

不为每两个品牌机械生成一篇内容重复的比较文章。

优先选择有真实比较需求、足够数据和明确用户价值的组合。

# 第十章：建立完整的用户搜索转化路径

## 10.1 核心转化链路

**搜索关键词 → 三级文章 → 相关二级专题或品牌评测 → 品牌比较 → 套餐详情 → 注册。**

例如：

用户搜索：

“20 元以内月付机场怎么选？”

进入对应的三级文章。

文章提供：

- 20 元预算的实际限制。
- 月付与年付折算区别。
- 可核实的套餐比较。
- 不同流量需求的建议。
- 2—4 个相关品牌评测入口。

用户进入品牌评测后，看到：

- 真实优缺点。
- 套餐和线路分析。
- 适合及不适合人群。
- 可比较的替代品牌。

再进入品牌详情页：

- 查看实际套餐。
- 阅读优惠条件。
- 点击注册入口。

## 10.2 不同长尾文章使用不同转化方式

### 教程文章

优先：

相关教程、客户端选择、问题解决。

品牌链接只在能够帮助完成任务时出现。

### 排障文章

优先：

修复步骤、错误原因、服务商支持和故障验证。

不能把故障排查强行变成购买广告。

### 价格文章

优先：

套餐比较、品牌评测、价格详情。

### 选择文章

优先：

品牌优缺点、同类比较、深度评测。

### 品牌评测

优先：

品牌商业详情、套餐选择和透明注册 CTA。

### 风险文章

优先：

核实信息、用户应对措施和条件明确的替代方案。

商业推荐不能代替必要的风险说明。

# 第十一章：全站内链自动映射

## 11.1 建立内容关系图

每篇三级文章至少应明确：

- 所属一级专题。
- 所属二级专题。
- 直接相关的三级文章。
- 相关的品牌评测（适用时）。
- 相关商业页面（适用时）。

每家品牌评测应明确：

- 上游推荐专题。
- 上游价格专题。
- 上游技术专题。
- 相关教程。
- 相关品牌比较。
- 品牌商业详情页。
- 资料与风险说明。

## 11.2 自动链接规则

在正文中合理插入：

- 上级二级专题。
- 相关操作文章。
- 技术解释页面。
- 真实品牌评测。
- 比较文章。
- 套餐详情。

链接必须存在，且对用户下一步有明确帮助。

同一篇文章不应机械重复插入多个相同品牌链接。

## 11.3 禁止孤立页面

所有正式发布的三级文章都应当能从至少一个相关专题或有效站内入口被发现。

品牌评测应能从品牌库、相关专题推荐或品牌商业页进入。

品牌商业页应提供返回评测和套餐比较的路径。

新增文章需要自动更新对应站内索引。

避免每次新增一篇文章都必须手工修改十几个页面。

# 第十二章：SEO 技术标准

## 12.1 页面基础 SEO

每个可索引页面必须包含：

- 唯一 Title。
- 唯一 Meta Description。
- 唯一 H1。
- 合理 H2/H3。
- Canonical。
- Open Graph 信息。
- Breadcrumb。
- 真实发布时间。
- 实际更新时间。
- 图片 alt。
- 正文可读的静态 HTML。
- 有效内部链接。

## 12.2 VitePress 实现

使用 Markdown Frontmatter 管理文章元数据。

例如：

- title
- description
- date
- updated
- author
- category
- tags
- pillar
- parentTopic
- primaryKeyword
- searchIntent
- relatedSlugs
- relatedBrands
- faq
- draft

建立与当前项目兼容的必要类型检查和数据索引脚本。

对于内容列表、相关文章和品牌推荐组件，优先通过构建阶段的数据处理生成可读取的 HTML。

继续使用现有 Pagefind、Sitemap 和 Apache 部署结构。

## 12.3 结构化数据

按真实页面类型使用：

- Article / BlogPosting。
- BreadcrumbList。
- WebPage。
- Service（适用时）。
- ItemList（适用时）。
- 其他符合实际页面语义的 Schema。

FAQ 必须是正文中真实可见的问答；结构化标记只在适用时使用。

不编造 AggregateRating、Review 或 Product Offer。

## 12.4 关键词竞争检查

检查：

- 三级文章之间的重复搜索意图。
- 三级文章与二级专题的重叠。
- 品牌评测与商业详情页的关键词重叠。
- 两篇品牌对比文章的重复主题。
- 年度内容与常青内容的冲突。
- 同一主题的多个 URL。

发现高度重叠时优先考虑：

- 合并正文。
- 调整目标意图。
- 保留权威页面。
- 设置合理内链。
- 必要时使用 301 重定向。

不要把 Canonical 当成解决所有重复内容的万能手段。

# 第十三章：GEO/AEO 内容优化

## 13.1 Answer-First

所有核心文章和评测必须直接回答主要问题。

例如：

“Clash Verge 订阅导入失败怎么办？”

开头先说明排查顺序。

“光速云怎么样？”

开头先说明品牌定位、主要特点、限制以及资料日期。

“IEPL 与 IPLC 有什么区别？”

开头先提供简明定义和可理解的差异。

不要在答案前加入大量无关背景。

## 13.2 实体语义

建立以下关系：

品牌 → 套餐 → 线路 → 协议 → 客户端 → 节点 → 使用场景。

客户端 → 操作系统 → 软件版本 → 配置方式 → 常见故障。

问题 → 症状 → 原因 → 检查步骤 → 解决方法。

价格 → 付费周期 → 流量 → 倍率 → 实际成本。

将实体名称、别名和对应 URL 统一管理。

## 13.3 可引用的信息表达

重要结论应具备：

- 准确答案。
- 必要的适用条件。
- 真实参数。
- 资料来源。
- 时间。
- 比较依据。
- 合理的不确定性说明。

GEO 目标是让内容更容易被发现、理解和引用，而不是通过关键词密度操纵 AI 搜索。

# 第十四章：文章配图与品牌评测图表

## 14.1 三级文章配图

按需使用：

- 客户端界面截图。
- 操作步骤截图。
- 技术概念图。
- 故障判断流程。
- 参数解释图。
- 价格比较图。

图片必须服务正文内容。

实际软件界面截图应与相应版本一致。

概念图应清楚标注为示意图。

## 14.2 品牌评测图表

复用现有品牌图表系统：

- 深色专业监控面板。
- 清晰指标。
- 品牌独立 Accent Color。
- 数据状态。
- 测试时间。
- 节点地区。
- 来源信息。

不同品牌使用相同的底层组件逻辑，但根据实际数据生成不同的信息展示。

不要将全部品牌做成只有名称和颜色不同的重复海报。

# 第十五章：商业链接与转化管理

## 15.1 统一品牌推广链接

从品牌数据库读取：

- officialWebsite。
- affiliateUrl。
- couponCode。
- couponConditions。
- pricingPlans。
- verifiedAt。

不得把所有品牌误导至同一个不相关的注册入口。

如果项目已有明确的全局商业跳转策略，先核实其适用品牌与当前配置，不得覆盖来源更具体的品牌链接而不记录原因。

所有推广链接统一使用：

`target="_blank" rel="nofollow sponsored noopener"`

并在相关位置提供清楚的推广关系披露。

## 15.2 CTA 内容

根据页面选择：

- 查看深度评测。
- 比较品牌。
- 查看套餐价格。
- 了解优惠条件。
- 查看官方注册入口。
- 阅读安装教程。
- 查看相关替代方案。

不在每个 H2 下重复放置注册按钮。

## 15.3 转化事件

如项目已有统计工具，可记录：

- article_view
- review_click
- comparison_click
- pricing_view
- affiliate_click

仅在获得真实订单或合法授权的数据时，才可以统计实际注册和付费转化。

不将 CTA 点击冒充购买成功。

# 第十六章：内容质量与去重系统

## 16.1 自动检查

建设文章检查脚本，至少检测：

1. 重复 Title。
2. 重复 H1。
3. 主关键词竞争。
4. 高度相似正文。
5. 空白文章。
6. 无来源的关键数字。
7. 过期的时间敏感数据。
8. 失效内链。
9. 缺失评测入口。
10. 重复品牌 slug。
11. 缺少主要搜索答案。
12. 错误的文章归属。
13. 错误的套餐价格口径。
14. Schema 与实际正文不一致。

## 16.2 防止批量低质量内容

不允许：

- 将一篇文章简单替换关键词后批量发布。
- 给所有文章加入同样的前言和结尾。
- 机械增加 FAQ 凑字数。
- 复制品牌官网宣传作为独立评测。
- 虚构用户评价。
- 虚构亲自使用经历。
- 把旧测试结果当成实时测量。
- 为不存在的文章生成可索引空白页面。

文章数量不能代替内容质量。

保证每家品牌评测之间具有真实差异。

## 17.5 第五阶段：商业详情

检查每家品牌是否存在：

- 实际品牌详情页。
- 可核实套餐。
- 对应评测。
- 统一推广链接。
- 风险说明。
- 手机端可操作的 CTA。

补充缺失内容。

## 17.6 第六阶段：品牌比较

优先制作具有明确比较需求和可用数据的文章。

不机械生成所有品牌两两对比。

## 17.7 第七阶段：内链与 SEO/GEO

完成：

- 三级文章到二级专题的归属。
- 三级文章之间的互链。
- 相关文章到品牌评测的关联。
- 评测到品牌商业页的连接。
- 品牌库与评测页的关联。
- SEO 元数据。
- JSON-LD。
- Sitemap。
- Pagefind 索引。

## 17.8 第八阶段：构建与验收

运行 VitePress 构建及相关内容检查。

实际验证文章 URL、重要链接、页面内容和品牌 CTA。

保存最终检查报告。
