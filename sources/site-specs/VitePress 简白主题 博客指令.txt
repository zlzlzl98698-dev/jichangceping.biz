# 第一部分：网站商业定位与整体架构

## 1. 网站定位

本项目不是普通的机场资讯博客，也不是只有排行榜和注册链接的导航站。

它是一个以 Google/Bing 自然搜索为获客入口，以深度教程、客观评测、价格比较、品牌选择与商业页面完成转化的中文内容网站。

核心业务链路：

**核心关键词 → 长尾关键词 → 用户搜索需求 → SEO 专题集群 → 独立文章页面 → 自然搜索流量 → 品牌评测 → 套餐比较 → 品牌商业页面 → 注册转化。**

围绕以下十个搜索市场建立长期内容优势：

1. 机场推荐与排行榜
2. 价格与套餐选择
3. 机场品牌与深度评测
4. VPN 与加速器
5. 代理客户端软件
6. AI 与流媒体使用
7. 线路与节点技术
8. 安装配置与使用教程
9. 连接故障与问题排查
10. 风险预警与替代方案

网站必须提供真正的决策价值，而不是简单重复关键词。

## 2. 一个域名，三套独立内容体系

建立三套逻辑独立、相互关联、共享统一 SEO/GEO 技术架构的内容体系。

### A. 教程与知识体系：负责获取搜索流量

面向新手、中级用户和高级用户。

包含：

- 客户端介绍和下载指南
- 客户端安装与配置
- 机场订阅导入
- 网络协议知识
- 分流规则设置
- TUN 模式介绍
- 设备兼容性
- AI 工具使用问题
- 网络故障排查
- 线路和节点知识
- 免费工具及替代方案

教程页面需要独立回答实际问题。

不要求每篇教程直接推销品牌；优先解决问题，再根据上下文提供相关评测入口。

### B. 评测与比较体系：负责辅助用户决策

包含：

- 单品牌深度评测
- 品牌优缺点分析
- 套餐比较
- 线路特点比较
- 节点地区比较
- AI/流媒体表现
- 新手适用性
- 多设备兼容性
- 价格与性价比
- 同类品牌对比
- 风险和局限性

评测应建立清晰、可解释、可复核的比较标准。

不允许因为某个品牌存在推广链接就将其全部评价维度设为最高。

### C. 商业转化体系：负责完成选择与注册

包含：

- 机场品牌库
- 品牌详情和商业落地页
- 套餐价格卡片
- 优惠码展示
- 推荐适用人群
- 套餐选择建议
- 品牌注册入口
- 新手购买指南
- 品牌替代方案
- 透明推广链接披露

三套体系必须保持 URL 结构、内容定位及核心搜索意图的差异。

不要把教程、评测和商业落地页全部做成高度相似的推销模板。

# 第二部分：VitePress 技术架构

## 3. 技术栈

采用：

- VitePress：静态网站生成
- Vue 3：交互组件
- Markdown：文章和知识内容
- TypeScript：品牌及内容数据管理
- 原生 CSS / CSS Variables：统一设计系统
- Pagefind：全站静态全文搜索
- VitePress 内置 Sitemap：站点地图生成
- JSON-LD：适用页面的结构化数据
- Node.js 脚本：内容生成、关键词管理和质量检查
- Apache：静态文件托管

尽量避免引入复杂 UI 框架、大型数据库、SSR 服务或无必要的依赖。

优先选择构建期生成 HTML 的方式，让搜索引擎不执行 JavaScript 也能读取文章主体内容。

## 4. 建立清晰的项目目录

建议采用以下结构；如现有项目已有合理组织，可以在兼容的前提下调整。

- `docs/.vitepress/config.mts`：全站配置
- `docs/.vitepress/theme/`：主题与组件
- `docs/index.md`：网站首页
- `docs/recommend/`：机场推荐
- `docs/pricing/`：价格与套餐
- `docs/brands/`：品牌库与品牌商业页面
- `docs/reviews/`：独立品牌评测
- `docs/vpn/`：VPN 与加速器
- `docs/clients/`：客户端软件
- `docs/ai-streaming/`：AI 与流媒体
- `docs/routes/`：线路与节点
- `docs/tutorials/`：使用教程
- `docs/troubleshooting/`：故障排查
- `docs/risks/`：风险与替代
- `docs/compare/`：品牌对比
- `docs/public/`：静态资源
- `data/brands/`：品牌结构化数据
- `data/keywords/`：关键词数据
- `data/tests/`：测速及解锁数据
- `data/sources/`：资料来源与数据核验
- `scripts/`：自动化脚本
- `reports/`：分析与验收报告

项目直接放在当前工作目录，不额外创建无意义的外层父文件夹。

实际组织可优化，但数据、页面、组件、图片和脚本必须分工清晰。

## 5. 全局配置与部署

创建统一站点配置，包括：

- siteName
- siteUrl
- siteDescription
- siteLogo
- locale
- defaultAuthor
- primaryBrand
- socialLinks
- contactInfo
- canonicalBase
- affiliateDisclosure
- analyticsConfig

当域名尚未确定时：

- 允许使用本地开发环境正常运行。
- 不在正式可索引 HTML 中输出虚假的生产域名。
- Sitemap 和 canonical 使用同一个未来可配置的正式域名。
- 域名确定后通过环境变量或配置项重新构建。
- 缺少生产域名时输出明确的部署检查提示。

配置 VitePress 正式 Sitemap 功能。

配置 Pagefind 在 VitePress 静态构建完成后再执行索引生成。

提供：

- `npm run dev`
- `npm run build`
- `npm run preview`
- `npm run audit`
- `npm run keywords:update`

以及实际需要的其他维护命令。

Apache 部署需要支持静态资源、干净 URL、404 页面和缓存策略。如果启用 `cleanUrls`，必须提供经过验证的 Apache RewriteRule 或等效配置。

- Firefly 的重复条目和不同推广链接。
- 部分品牌不一致的运营年份。
- 年付折算价与真正月付价格的区别。
- 历史套餐与当前套餐的区别。
- IEPL、IPLC、普通中转和直连线路的证明依据。
- 专属客户端与第三方订阅是否真正兼容。
- 原文件中重复、缺失或跳号的榜单序号。

冲突未解决时，不得把其中任何一个值包装成经过验证的事实。

将冲突记录到 `reports/data-conflicts.md`，包含冲突字段、不同数值、来源文件、可用日期与建议核验方法。

# 第五部分：品牌库、独立评测与商业转化

## 13. 建立完整品牌库

品牌库不是单纯的链接集合。

需要包含：

- 品牌总览
- 关键词搜索
- 品牌卡片
- 价格筛选
- 线路筛选
- 客户端兼容筛选
- 适用场景筛选
- 品牌信息状态
- 最近更新时间
- 深度评测入口
- 套餐详情入口
- 相关比较入口

品牌数据与 UI 分离。

品牌卡片不能只有名称、Logo 和注册按钮，还需要显示具备来源的关键信息。

所有品牌必须有独立且有效的详情链接。

## 14. 每家品牌建立两个独立页面

### A. 独立深度评测页

示例：

`/reviews/guangsuyun/`

主要目标是回答：

这家品牌到底怎么样，适合谁，和其他选择有什么差异？

### B. 品牌商业详情页

示例：

`/brands/guangsuyun/`

主要目标是回答：

该品牌有哪些套餐，如何选择，优惠条件是什么，以及如何进入官方注册渠道？

两个页面应当在搜索意图、Title、H1、内容结构和页面功能上明显不同，避免重复页面互相竞争。

另设独立品牌比较页，例如：

`/compare/guangsuyun-vs-feimaoyun/`

不要把对比文章简单做成两个品牌页面拼接。

## 15. 万字级品牌深度评测矩阵

为每家品牌创建独立的深度评测文章。

**内容成熟时以 9,000—12,000 中文字为目标。**

文章长度建立在真实信息、测试分析、技术解释、使用步骤和有效比较的基础上。

当可靠资料不足以支撑万字时，优先完成信息准确的文章，并将待补充章节和数据缺口记录下来。不得通过套话、重复段落或虚构测试凑字数。

每篇品牌文章至少覆盖：

1. 品牌概况与核心结论
2. 适合及不适合的人群
3. 运营背景与资料来源
4. 主要卖点和局限
5. 套餐价格与选择建议
6. 年付、月付及不限时套餐分析
7. 线路类型与网络架构
8. 节点地区和覆盖能力
9. 协议及客户端兼容性
10. 速度与延迟表现
11. 晚高峰使用情况
12. AI 工具兼容情况
13. 流媒体解锁情况
14. 新手安装及使用方式
15. 多设备场景
16. 售后、退款及风险
17. 与同价位品牌比较
18. 实际优势和限制
19. 购买前注意事项
20. 常见问题
21. 数据来源及更新时间
22. 总结与下一步选择

这是内容覆盖清单，不是要求所有品牌机械采用完全相同的 22 个 H2。

每家品牌必须根据独有特征重新组织章节。

例如：

- 光速云：重点分析套餐层级、线路声明、客户端兼容和综合使用场景。
- 飞猫云：重点分析专属客户端、新手使用体验与兼容限制。
- 隐形人：重点分析专属客户端模式及第三方订阅限制。
- 二猫云：重点分析多设备使用、套餐层级与适用人群。
- 灵动云：结合资料中的历史测试记录，说明测试环境和局限。
- EdgeNova：重点解释多线路分配的产品定位，并标明未验证信息。

不同品牌需要不同的内容重点和真实信息增量。

## 16. 品牌商业落地页

每家品牌商业页面至少包含：

- 品牌 Hero 区域
- 一句话定位
- 核心功能介绍
- 适用场景
- 品牌特色
- 4—5 个主要套餐卡片（有真实数据时）
- 套餐横向对比
- 优惠码与条件
- 客户端适配
- 常见疑问
- 风险与售后提示
- 深度评测入口
- 注册 CTA

套餐卡片的价格和流量必须来自真实品牌数据。

如果原始资料不足 4 档，不得虚构套餐；只显示已有套餐，并保留可扩展的组件结构。

不同品牌可以共享数据结构和底层组件，但页面布局、卖点排序、视觉重点及内容组织需要体现差异。

# 第七部分：持续发现关键词的系统

## 19. 建立可扩展的 Keyword Discovery Engine

这是本项目的重要功能，不能只提供一次性关键词列表。

建立持续可维护的关键词工作流：

**种子关键词 → 长尾扩展 → 搜索意图分类 → 主题聚类 → 页面映射 → 内容生产 → 页面发布 → 数据监测 → 关键词更新。**

建立统一关键词数据库。

每条关键词记录至少包含：

- keyword
- normalizedKeyword
- topic
- cluster
- searchIntent
- userStage
- targetAudience
- device
- brand
- region
- modifier
- source
- searchVolume
- competition
- priorityScore
- targetUrl
- contentStatus
- lastCheckedAt

## 20. 关键词扩展规则

采用不同维度组合种子关键词。

### 品牌维度

品牌名 + 评测、价格、官网、怎么样、稳定吗、优惠码、退款、客户端、替代品。

### 价格维度

便宜、低价、月付、年付、一元、一分、优惠、性价比、大流量、不限时。

### 设备维度

Windows、Mac、Android、iPhone、iPad、Linux、OpenWrt。

### 技术维度

IEPL、IPLC、VLESS、Trojan、Mihomo、sing-box、Clash、DNS、TUN。

### 使用场景

ChatGPT、Claude、Gemini、Netflix、YouTube、远程办公、跨境电商、游戏。

### 问题维度

连接不上、超时、无法启动、更新失败、订阅为空、速度慢、没有节点、DNS 异常。

### 用户维度

新手、学生、轻度用户、重度用户、办公用户、多设备用户。

### 时间维度

最新、当年版本、更新、停运、价格调整、维护状态。

年度关键词必须匹配实际内容与发布时间，不得机械给所有文章加上最新年份。

## 21. 搜索意图分类

自动识别五类主要搜索意图：

1. Informational：信息学习
2. Navigational：寻找特定品牌或软件
3. Commercial Investigation：商业比较
4. Transactional：注册和购买
5. Troubleshooting：问题解决

为不同意图配置不同文章模板、URL、CTA 和内链规则。

例如：

“Clash Verge 如何导入订阅”应当归入教程。

“光速云怎么样”应当归入评测。

“光速云套餐价格”应当归入商业品牌页面。

避免三篇文章都使用同一个主要关键词。

## 22. 自动关键词聚类

建立关键词语义归类规则。

相同搜索意图、可以由同一篇文章完整回答的词，合并到同一个目标页面。

不同用户任务的关键词，拆分到独立页面。

建立关键词主页面映射表。

每个页面必须具有：

- 一个主要搜索意图
- 一个主要关键词主题
- 若干相关次级关键词
- 对应的专题归属
- 清晰的上游与下游链接

建立关键词冲突检测。

如果两个页面竞争高度相同的搜索意图，应提示：

- 内容合并
- 页面重新定位
- 标题调整
- 内链优化
- Canonical 处理
- 301 重定向（仅在确实需要时）

## 23. 关键词优先级评分

建立可修改权重的优先级机制。

参考维度：

- 搜索意图价值
- 商业转化关联度
- 当前主题覆盖缺口
- 内容制作难度
- 证据资料完整度
- 搜索需求证据
- 与现有页面的内链协同价值

不能将 AI 推测的搜索量当成 Google 或 Bing 的真实搜索量。

支持后期导入：

- Google Search Console CSV
- Bing Webmaster Tools CSV
- 已授权的关键词工具 CSV
- 站内搜索词
- 人工整理的关键词库

如果没有外部真实关键词数据，先建立候选词和内容优先级，搜索量及排名字段保留未知状态。

## 24. 持续更新机制

建设 `keywords:update` 工作流。

运行后自动：

1. 读取种子关键词。
2. 读取已有关键词数据库。
3. 合并用户导入的新数据。
4. 自动归一化和去重。
5. 识别长尾组合。
6. 分类搜索意图。
7. 推荐专题归属。
8. 查找已有对应 URL。
9. 检查关键词竞争。
10. 识别缺失内容。
11. 更新选题待办列表。
12. 生成关键词分析报告。

输出：

- `keyword-master.csv`
- `keyword-clusters.json`
- `keyword-opportunities.csv`
- `content-backlog.md`
- `keyword-cannibalization.md`

脚本必须能真实执行。

对于没有联网 API 的环境，不得虚构在线搜索结果；使用本地数据生成候选词，保留未来连接真实数据源的能力。

# 第八部分：SEO 技术架构

## 25. 每页独立 SEO

所有可索引页面必须具备：

- 唯一 Title
- 唯一 Meta Description
- 一个主要 H1
- 合理 H2/H3 层级
- 正确 Canonical
- Open Graph 信息
- 页面类型
- 发布时间
- 更新时间
- 作者或编辑信息
- 面包屑导航
- 真实相关内链
- 图片 alt
- 响应式图片
- 完整静态 HTML

避免出现：

- 重复 Title
- 重复 Meta
- 多个冲突 H1
- 空白专题首页
- 批量换词内容
- 伪原创薄内容
- 没有目标的标签页
- 无效内链
- 孤立文章
- 误导性的年份或更新日期

## 26. Sitemap 与 Robots

正式部署时生成：

- `sitemap.xml`
- `robots.txt`
- 自定义 `404.html`

Sitemap 仅纳入可索引、实际存在、具有价值的页面。

草稿、空白占位页、无结果搜索页、低价值筛选参数页不应进入正式 Sitemap。

在内容更新时同步维护真实更新时间。

如需要单独生成 RSS，应采用与 VitePress 兼容的轻量实现。

## 27. 结构化数据

建立可复用 JSON-LD 系统。

按页面类型选用：

- Organization
- WebSite
- BreadcrumbList
- Article / BlogPosting
- ItemList
- SoftwareApplication
- Service
- 其他确实适用的 Schema

不要向所有页面机械注入同一套 Schema。

FAQ 在页面中保持真实、完整、可见的问答内容；结构化标记仅在语义适用时采用，不将 FAQ 富结果作为 Google 排名保证。

JSON-LD 必须与页面中实际展示的信息一致。

不添加虚假 AggregateRating、用户评价、星级评分或不存在的产品报价。

## 28. 内容内链与抓取深度

建立：

**首页 → 一级专题 → 二级专题 → 文章 → 相关评测 → 品牌详情 → 注册入口**

重要页面尽量保持三次点击内可发现。

所有文章根据用户需求配置：

- 所属专题
- 同主题延伸文章
- 前置知识
- 下一步教程
- 相关品牌评测
- 品牌比较
- 商业详情页

不能每篇文章都机械插入相同品牌的多个关键词链接。

网站需要具备：

- HTML 可抓取导航
- 自动面包屑
- 相关文章模块
- 专题聚合模块
- 品牌内容关联
- 失效链接检测
- 孤立页面检测

# 第九部分：AI 搜索与 GEO/AEO 深度优化

## 29. Answer-First 内容策略

所有主要内容采用答案优先。

每篇文章开头直接回答用户的核心问题。

例如：

用户搜索“IEPL 和 IPLC 有什么区别”，文章开头应该给出明确、易理解的区别及适用条件。

用户搜索“某品牌怎么样”，文章开头应说明品牌定位、适用人群、主要限制和资料更新情况。

不要用大量空泛前言推迟回答。

## 30. 实体关系体系

针对每篇文章建立：

**核心实体 → 相关概念 → 技术参数 → 使用场景 → 评价依据 → 对比对象 → FAQ。**

实体类型包括：

- 品牌
- 套餐
- 客户端
- 操作系统
- 网络协议
- 线路类型
- 节点地区
- AI 服务
- 流媒体平台
- 故障类型

建立统一实体命名和别名表。

例如 Clash Verge 与 Clash Verge Rev 不应在不了解版本关系时无条件视为完全相同的产品。

每个实体应可以关联到站内相应的解释页面。

## 31. 让答案具备独立引用价值

重要内容提供：

- 简明结论
- 概念定义
- 有依据的数据
- 清晰对比表
- 条件化判断
- 可复现步骤
- 信息来源
- 最近核实日期

优先提供真实的信息增量。

允许使用独立答案段落和可理解的标题，提高信息抽取便利性。

但不使用隐藏关键词、批量问答填充或声称可以操纵 AI 回答的特殊标记。

GEO/AEO 目标是提高被理解、检索和引用的机会，不承诺任何平台的收录或推荐结果。

# 第十部分：统一视觉与页面组件

## 32. 网站整体设计

**现代中文科技资讯博客 + 专业品牌评测平台 + 轻量商业决策工具。**

- 白色页面背景

- 充足的正文留白
- 统一的卡片圆角
- 适当阴影和分隔线

# 第十一部分：推广链接与转化跟踪

## 35. 统一推广链接数据库

从品牌资料中提取各品牌对应的推广链接。

建立集中管理文件，例如：

`data/affiliate-links.ts`

同一个品牌在品牌详情、评测、比较表及推荐卡片中的推广链接，必须调用同一个数据源。

不允许在几十篇文章中分别硬编码链接。

原有推广链接有冲突时，进入审核报告，不得自动改写未知参数。

所有确认的推广链接统一使用：

`target="_blank" rel="nofollow sponsored noopener"`

并在相应位置提供清晰的推广关系说明。

使用透明的商业披露，不误导用户认为推广排序是完全独立、无利益关联的排行榜。

## 36. 转化漏斗

按用户决策阶段建立合理路径：

教程页面 → 相关知识 → 选择指南 → 品牌评测 → 套餐详情 → 注册 CTA。

比较文章 → 品牌优劣 → 价格对照 → 商业详情 → 注册 CTA。

品牌搜索 → 品牌库 → 品牌详情 → 评测/套餐 → 注册 CTA。

需要配置可选的 CTA 事件记录。

允许在用户配置统计工具后记录：

- 页面浏览
- 内部品牌详情点击
- 套餐查看
- 注册按钮点击

不得把点击注册按钮直接统计为真实付费购买。

不建立未经授权的用户追踪机制。

# 第十三部分：内容生产标准

## 38. 深度文章要求

普通教程：根据问题复杂度提供完整、可执行的解答，通常目标为 2,000—4,000 中文字。

核心专题：通常目标为 4,000—7,000 中文字。

品牌深度评测：资料充分时以 9,000—12,000 中文字为目标。

内容价值高于机械字数要求。

所有文章应优先采用：

- 真实问题
- 明确结论
- 具体步骤
- 可解释指标
- 场景差异
- 适用边界
- 数据来源
- 合理的比较分析

不同文章不要套用完全一致的引言、正文顺序和结尾。

## 39. 防止内容重复与关键词竞争

建立内容检查脚本，检测：

- 重复文章标题
- 重复 H1
- 主要关键词冲突
- 高度相似正文
- 重复 Meta Description
- 相似商业页面
- 无价值的薄专题页
- 大量相同的 CTA 语句
- 不存在的页面链接
- 数据来源缺失

不采用靠随机替换同义词规避搜索引擎识别的方式。

必须通过真实内容差异提高原创价值。
